# 通用-编码实现与变更控制规范

> 版本：v1.0（模板通用版，自实例编码规范瘦身回流）
> 状态：现役
> 适用范围：软件系统的编码实现阶段（含框架搭建与逐模块填充）。实例使用前须评估与自身技术栈的差异。
> 相关入口：本目录其他规范；空卡模板见 `_workspace/_表单/_模板-编码任务卡.md`。

## 1. 目的与边界

本规范定义编码实现阶段的最小要求：任务如何拆分与记录（任务记录卡）、代码如何与设计保持可追溯、实现偏差与设计变更如何控制、新会话如何接力、**跨模型交接如何检查**。

本规范不定义任何具体项目的模块划分、任务清单、接口签名或代码内容。这些内容必须在项目的唯一事实源中维护，本规范只给要求与组织方式。

**本规范的第一目标：任务记录的第一读者是下一个 AI 会话**——任何新开的窗口或更换的 AI，读完任务卡即可接续工作，不需要人重新交代上下文。

## 2. 术语与强制级别

| 术语 | 定义 |
|---|---|
| 任务 | 一个可独立完成、独立验证的最小工作单元（一个子系统通常拆为 3～8 个任务）。 |
| 任务记录卡（任务卡） | 一个任务的全程记录：做什么、依据什么、怎么做、遇到什么问题、验证结果、偏差与决定。编码阶段的最小记录单位。 |
| 任务号 | `T-<子系统>-<序>` 形态（如 T-M2-01），与项目编号体系并列；一号终身不复用。 |
| **执行模型** | 实际编码该任务的 AI 模型，以 `provider/model` 记录；一个任务多模型接力时逐段注明。 |
| **模型来源** | 模型标识的取得方式：交互选择、显式参数或宿主环境变量名。不得从提交、代码或产品名称推断；追溯历史可写「精确型号未知」。 |
| **交付证据检查** | 后继任务开工前，对**时间顺序上的上一已完成任务**执行 §5.1 六项机械核对。它验证提交、验证、记录与追溯证据，不替代语义审查或依赖检查。 |
| **语义核对** | 对被检查任务的驱动依据、验收条件、边界和负向场景逐项抽查代码与验证证据，见 §5.2。它用于发现「测试已过但实现遗漏」的情况。 |
| **直接依赖核对** | 对即将开工任务卡中声明的全部前置任务、接口和数据契约逐项核对，见 §5.3。检查对象可以不同于时间顺序上的上一任务。 |
| **模型独立性** | 检查模型与被检查任务执行模型是否不同。不同模型是优先选择；同模型允许，但必须记录原因，避免把共同盲区误判为独立复核。 |
| **交接检查记录** | 一次实际发起的交付证据检查和语义核对的完整事实记录。记录按发生顺序编号，并保留检查时间、触发方式、检查模型与各项结果。 |
| **交接检查归纳** | 对同一任务全部交接检查记录的汇总：检查次数与身份、稳定共识、差异或冲突、未决项及其处置。归纳不替代任何原始记录。 |
| **模型缺陷观察** | 交接检查与执行过程中发现的问题，逐条定因后记入观察日志，跨任务积累用于分析模型所长与优化卡的陈述方式。 |
| 实现偏差 | 代码与驱动依据不符，且属于实现侧可修正的差异。 |
| 设计缺口 | 驱动依据本身不足以支撑实现，须回设计补足的差异。 |
| 驱动依据 | 任务所依据的设计文档/图表及其具体章节（到节号，不到节号=未定位）。 |
| **验证环境** | 实际执行验证命令的环境，含运行时版本（Node/Electron/浏览器）与数据路径。涉及嵌入运行时的能力，验证环境必须等于该能力实际运行的运行时环境，宿主/系统环境不得代验。 |

`必须` 和 `不得` 表示强制要求。`应` 表示通常需要满足，例外必须登记原因。`可以` 表示可选做法。

## 3. 任务拆分

1. 子系统（对应一册设计文档或等价设计依据）开工前必须先拆任务，一任务=一个可独立验证的构件或场景。
2. 拆分粒度判据：每个任务有独立的验证锚点（一条命令/一个用例/一段可复跑输出）；无独立验证锚点的工作并入相邻任务。
3. 子系统完成判据（设计文档内验证方式）本身不单独立任务——它是最后一个任务的验收内容。
4. 任务必须在开工前登记任务号并建卡；不得边做边补卡（追溯补卡见 §8）。
5. 不预先拆分未开工子系统的任务——开工时才知道真实边界，预拆必返工。

### 3.1 结构健康检查（编码期强制）

适用对象为手写生产代码；生成物、依赖锁文件、fixture、样例资产、清单和第三方代码不适用本节的规模信号。结构健康检查不以文件行数裁定好坏，行数只用于触发人工复核。

1. 任务开工前，执行者必须判断新增能力属于既有职责、既有模块的内部实现，还是应建立新的物理模块；结论写入任务卡「实现记录」。
2. 每次提交前，受影响手写生产代码必须检查职责单一性、公共入口边界和依赖方向，并记录实际执行的静态检查或可重复命令。
3. 公共入口或聚合文件默认只允许导出、注册或装配；不得继续加入彼此独立的业务实现。共享类型和契约必须放在可单向依赖的独立位置，低层模块不得反向导入上层公共入口。

| 触发级别 | 信号 | 必须处置 |
|---|---|---|
| 观察 | 单任务令一个手写文件净增不少于 250 行，或相对任务开始时增长不少于 30% | 在任务卡登记职责与物理边界复核；未发现漂移也须如实记录 |
| 计划 | 一个文件含两个以上可独立验证、可独立演进的职责，或公共入口已承载业务实现 | 创建拆分任务，并在当前里程碑出口前完成或登记经评审的例外、风险与回退方案 |
| 阻断 | 将新的无关业务继续加入已混杂的公共入口/聚合文件，或形成跨层反向依赖、循环依赖 | 先完成模块拆分或设计变更；不得开始该无关业务实现 |

阈值只触发检查，不因单一数值自动判定为问题。结构高度内聚的状态机、解析器等可保留在单文件中，但必须在任务卡中说明其单一职责、验证范围和不拆分原因。

### 3.2 工作树策略（编码期强制）

1. 默认在用户日常可见的代码仓主工作目录执行任务。不得把「每任务新建独立 worktree」作为默认做法。
2. 只有用户明确授权，或已在任务计划中登记确有并行隔离需要时，才可以创建附加 worktree。创建前必须说明物理路径、分支、隔离目的和任务卡所在位置。
3. 任务卡必须可在主工作目录的 `docs/tasks/` 直接查阅，不得只保存在附加 worktree。附加 worktree 中产生的任务卡、门禁记录和已验证提交，必须在任务结束前合入或迁入主工作目录。
4. 关闭附加 worktree 前，必须核对其工作区状态并保全需要保留的未提交内容；删除后在任务卡或续接记录登记迁入的提交和删除原因。

## 4. 任务记录卡（核心机制）

### 4.1 位置与命名

- 卡目录：代码仓 `docs/tasks/`（卡与代码同仓同生命周期，一任务的代码与其卡同 commit 提交）。
- 命名：`T-<子系统>-<序>-<短名>.md`。
- 索引：卡状态一览表放 `docs/tasks/README.md`（任务号×状态×commit）；项目文档仓的实现对照表（如有）只登记任务号与结果，不复制卡内容——卡是唯一事实源，防第二事实源。

### 4.2 卡结构（十节，固定）

空卡模板见 `_workspace/_表单/_模板-编码任务卡.md`，十节如下：

1. 状态（附接手点一句话——新 AI 从这里继续）
2. 执行模型（provider/model+来源；多模型接力逐段注明）
3. 开工依赖核对（待开工门禁回填）
4. 交接检查（追加记录与归纳，append-only）
5. 做什么（一两句话+验收口径）
6. 驱动依据（设计文档/图表+节号；数据文件给绝对路径或登记表指向——写到「新 AI 不用问人就能定位」的程度）
7. 实现记录（文件清单+关键实现决定）
8. 遇到的问题（逐条：现象→原因→处置；没有问题写「无」。环境与数据的坑必须记——不记，下个会话原样再踩）
9. 验证（命令/用例号+实际输出摘要+结果 PASS/FAIL）
10. 偏差与决定（与驱动依据不符处：实现偏差改码或设计缺口走变更登记；没有写「无」，不得留空——这是审核的主要抽查对象）+ 追溯（commit 号↔对照表行↔用例号）

### 4.3 填写规则

1. **「驱动依据」与「遇到的问题」「偏差与决定」三节必填**（无内容写「无」），其余节按实填写；「执行模型」行必须填 `provider/model` 与来源；「开工依赖核对」由本任务首次开工门禁回填。后继任务开工者将交接检查追加到被检查卡；主动复检者也可以追加记录，但不得改变任何任务状态或开工依赖。本任务执行前、中、后均不填写自身的「交接检查」节。
2. PASS 必须实际执行验证并贴输出摘要，不得凭印象记 PASS。**验证必须在该能力实际运行的运行时环境下执行**——涉及嵌入运行时（Electron/内嵌 Node/浏览器等），必须以该运行时实际运行，宿主/系统环境不得代验；卡「验证」节必须记录验证环境（运行时版本、数据路径），未记录的 PASS 视为证据不足。
3. 进行中任务的「状态」行必须能让新 AI 直接接手——写清当前进行到哪、下一步是什么。
4. 写完自检一句：**换个一无所知的 AI，照这张卡（加上它引用的文档）能不问人接续吗？** 答不出「能」就补。
5. 卡内容从简（关键处两三行即可），不写给人看的修饰；审核只抽查三样：依据节号对不对、验证命令跑不跑得出同样结果、偏差节是否如实。

## 5. 交接开工检查（开工前工序）

**标准触发时机**：每次开始**后继任务**时。任务中途换会话或切换模型不自动产生检查；该任务完成后由其后继任务执行者检查。

**主动复检**：任何已完成任务可以由项目成员、后继执行者或不同模型主动发起额外检查。主动复检不改变被检查任务或任何后继任务的状态，不替代标准开工门禁，也不得以「已有 PASS」为理由省略六项和语义核对。其记录必须写明发起原因，并与历史记录并列保存。

**检查分层**：本节包含交付证据检查（§5.1）、语义核对（§5.2）和直接依赖核对（§5.3）。三层共同构成开工门禁，不能以任一层 PASS 替代其他层。

**交付证据检查对象**：时间顺序上的上一个已完成任务（按卡状态表顺序；前驱为追溯卡时同样适用）。它是质量抽检对象，不声明为当前任务的功能前置。

**记录责任和位置**：标准检查由即将开工任务的执行者完成。交付证据检查与语义核对记录追加到**被检查任务卡**；直接依赖核对写入**即将开工任务卡**的「开工依赖核对」行。主动复检只追加被检查卡的交接检查记录，不写任何其他任务卡。不得在被检查任务的执行前、中、后预填其交接检查。

**检查依据**：每次必须列出实际核对的材料和位置，至少覆盖卡内验证命令及输出、commit/工作区状态、实现文件清单、对照表行和待复核项；不能只写「已检查」或只给结论。

### 5.0 多记录追加与归纳（强制）

1. 每次实际检查必须新建下一顺序号记录。不得编辑既有记录的检查依据、模型、结果、问题或结论；勘误只能在新记录中说明原记录位置、勘误原因和更正事实。
2. 每次追加后必须更新「归纳总结」。归纳至少包含记录数与检查模型、所有记录一致的结论、分歧或检查范围差异、未决项及其处置。不同模型得到相同结果只能增加交叉佐证，不得写成绝对正确。
3. 记录间存在 PASS/FAIL 冲突、运行环境不一致或语义覆盖范围不同，必须先定因（实现/卡表述/环境数据/混合），再决定返工、补验证、更新卡或继续跟踪。冲突未处置前不得把归纳写成「全部 PASS」。
4. 首次检查可以写「无横向差异」；第二次及以后不得只重复最新记录摘要，必须与全部既有记录比较。未发现差异也必须明确写「与检查 N…一致」。

### 5.1 交付证据检查（六项，全部机械核对）

| # | 检查项 | 核对方式 |
|---|---|---|
| 1 | 上一卡状态=已完成→其记载 commit 真实存在；工作区干净 | `git log` 对卡内 commit；`git status` |
| 2 | **上一卡「验证」节的命令原样复跑，结果与记载一致，且验证环境与运行时一致** | 逐条执行卡内命令，比对输出摘要；核对验证环境是否等于能力实际运行环境，不一致按中等问题处置并定因 |
| 3 | 卡「实现记录」列出的文件与该 commit 变更清单吻合 | `git show --stat <commit>` 对卡 |
| 4 | 「遇到的问题」「偏差与决定」非空（「无」也算）；「驱动依据」有节号 | 读卡 |
| 5 | 实现对照表已登记该任务行且结果一致（无对照表机制的项目记「无此机制」） | 对表 |
| 6 | 上一卡登记的「待复核」事项有下文或仍在跟踪 | 读卡+查后续卡 |

### 5.2 语义核对（强制）

1. 从被检查任务卡提取「做什么」、驱动依据的具体节号、验收口径和「偏差与决定」。小任务必须逐条核对；较大任务至少覆盖所有错误码、权限/只读边界、数据契约、异常路径、性能或缓存约束，以及一条负向场景。
2. 每个抽查项必须记录「依据或验收条款 → 代码位置 → 验证命令/用例及输出」。只写文件名或「已阅读代码」不构成核对证据。
3. 测试已 PASS 但没有覆盖条款时，记录为覆盖缺口。覆盖缺口至少按中等问题处理：补测试、登记待复核项，或说明为何当前任务不受影响。不得把未覆盖条款写成 PASS。
4. 语义核对发现实现遗漏时，按 §5.4 的重级问题处置；发现卡的验收口径无法判断时，定因写「卡表述」或「设计缺口」，不得猜测补全。
5. 对受影响的手写生产代码复核 §3.1：公共入口是否仍只承担导出/装配，新增职责是否仍可由一个模块一句话描述，低层模块是否反向依赖上层公共入口。命中信号而未登记处置时，语义核对不得写为 PASS。

### 5.3 直接依赖核对（强制）

1. 从**即将开工任务卡**的「前置」、驱动依据和接口/数据路径中列出全部直接依赖。若无直接依赖，明确写「无」并说明依据。
2. 对每个依赖记录「依赖任务或契约 → 实际版本/位置 → 当前任务如何使用」。时间顺序上的上一任务不是直接依赖时，必须明确标为「质量抽检对象，非功能前置」。
3. 任一直接依赖未完成、接口未冻结或数据契约不成立时，不得开始当前任务；应改为阻塞或先处理依赖。该检查避免并行任务只检查前一卡而遗漏真实前置。

### 5.4 模型独立性与发现问题的处置

检查模型应优先不同于被检查任务执行模型。模型相同不阻断任务，但必须在卡中记录原因。上一任务执行模型精确型号未知时，记录「无法比较」，不得伪造独立性。不得把 `claude`、`gpt` 等产品族名伪装成精确型号。

| 级别 | 情形 | 处置 |
|---|---|---|
| 轻 | 漏登记（对照表缺行/卡缺必填节） | 当场补齐，记入被检查任务卡「交接检查」节 |
| 中 | 复跑结果与记载不符（命令过时/输出漂移/环境变化） | 修验证或记原因；不改结论级 |
| 重 | 实质问题（复跑 FAIL/代码缺失/commit 不存在） | 上一卡状态改「返工中」；本任务若依赖其成果，先协助返工或绕开并记依赖关系 |

**每条发现（无论级别）必须定因**——四选一（可组合标「混合」）：

| 定因 | 判据 |
|---|---|
| 模型缺陷 | 上一执行模型明知规则未做到（如未跑验证记 PASS/漏看依据节号） |
| 卡表述 | 卡本身没说清（依据节号缺失/验收口径模糊/坑未预告）——此类直接驱动卡的写法优化 |
| 环境数据 | 环境或数据变化所致（盘符/格式/依赖版本），与执行者无关 |
| 混合 | 上述两类及以上各占成因 |

### 5.5 模型缺陷观察日志

- 位置：代码仓 `docs/tasks/model-observations.md`（与卡同仓同生命周期）。
- 形态：append-only 表格，一行=一条发现（时间/任务/定因/现象/处置）；字段含任务类型、检查层、模型独立性、严重度。
- 写入时机：交接检查发现问题时必写；任务执行中自省发现的自身模型缺陷也应写（执行模型=检查模型，如实标注）。
- 模型字段必须使用 `provider/model`；来源填「交互选择」「显式参数」或环境变量名。历史追溯无法确认精确型号时，保留已知厂商/族名并标注「精确型号未知」，不得猜测补写。
- 用途：按「执行模型 × 检查模型 × 任务类型 × 检查层」分析不同模型的易错模式；识别卡的陈述方式需优化之处。**局限须认知**：样本量小、任务混杂，结论定位为「模式观察」而非统计结论。
- 日志不承载处置结论（处置在卡内闭环），只承载观察数据。

## 6. 执行流程

```
子系统开工
  → 拆任务（§3）建卡（全部任务号+卡骨架一次建好）
  → 逐任务：对时间上一任务做交付证据六项+语义核对，对当前任务做直接依赖核对（§5，检查记录追加到被检查卡并更新归纳；发现入观察日志）→ 本任务实现 → 验证 → 填卡（执行模型/问题/偏差即时记）→ 提交（代码+卡同 commit）
  → 全任务完成 → 子系统完成判据验证 → 最后一卡记录结果
  → 项目文档侧：实现对照表登记任务号与结果（不复制内容；无对照表机制的项目可省）
```

1. 一任务的代码与其卡必须同 commit 提交（卡即结构化的提交说明）。
2. 任务中途换会话：新会话按 §7 接力链定位到进行中的卡，从「状态」行接手；仅在开始新的后继任务时执行 §5 的三层检查并回填上一卡。
3. 任务失败返工：卡状态改「返工中」，问题记入「遇到的问题」，不删旧记录。
4. 根因未收敛不得开始修改：当验证结果与运行时现象矛盾（验证全绿但运行失败）时，先核对验证环境与运行时环境一致性，逐层收敛根因（技术→过程→设计），写出根因分析后再从干净基线实施；禁止在根因未明时修改草案或提交。

## 7. 新会话接力链

新窗口/更换 AI 的定位路径（每层只指下一层，不跳级）：

```
_handoff/README.md（续接索引）
  → 当前阶段续接文档「新会话怎么接」
    → 实现对照表（哪张卡在进行中；无对照表则看卡状态一览 docs/tasks/README.md）
      → 即将开工任务的上一张已完成卡（先追加交付证据+语义核对并更新归纳；再核对当前任务直接依赖；按 §5 回填）
        → 进行中的任务卡（读「做什么/到哪了/有什么坑/下一步」）
          → 卡内「驱动依据」节号直达设计文档
```

治理要求：代码仓 README 必须有一行指引指向 `docs/tasks/`（防止 AI 进入代码仓而看不到卡）。

## 8. 追溯补卡（对已完成的既有工作）

对建卡机制之前已完成的工作：

1. 必须补卡，卡头标注「追溯」——按已发生的事实填写（实现记录/验证/结果），依据现存的提交记录与文档记载还原；
2. 遇到的问题一节按记忆与提交信息尽量还原，无法还原的写「未记录（建卡机制前完成）」；
3. 追溯卡的验证节：验证命令必须当前可复跑（复跑一遍再记 PASS，不得照抄历史结论）；
4. 追溯卡不用于评审当时做法的优劣，只补齐记录链的完整性。

## 9. 变更控制

1. 实现偏差：改代码对齐设计；改后在卡「偏差与决定」节登记现象与修正。
2. 设计缺口：不得在代码里自行发明设计——停任务，走项目的变更机制登记，设计侧补足后回任务。
3. 接口签名、错误码、绑定表等冻结基线不得因实现便利而擅自变更；变更一律先登记后改码。
4. 编码期自由度（已在设计侧显式豁免的，如 DDL 字段级、内部类型展开）：卡「实现记录」节登记选择即可，不算偏差。

## 10. 后续细化

首个子系统实跑后，按实际偏差回填修订本规范（拆分粒度是否合适/卡字段是否够用/接力链是否走通）。新增内容不得改写本规范已定义的任务卡机制与变更控制边界。
