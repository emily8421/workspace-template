# 通用文档管理原则（A1-A7）

> 适用所有目录与任务，与目录索引 / 跨目录约束 / git / 续接共同构成治理规则。
> 业务结构（某实例分几个目录、装什么）由实例自定，本原则不管「管理什么」，只管「怎么管理」。

## A1 唯一事实源锚点

- 每个主题约定**一个固定命名/位置的锚点文件**（如 `00-事实源-<日期>.md`），作为该主题唯一事实源。
- 其余相关材料用**链接指向锚点**，不复制内容、不另立源头。
- 范围变更时：旧文档一律**降级/归档**（见 A2），不保留两份并列的「现行」事实源。

## A2 范围变更 → 整体归档、重建新树

- 需求/结构范围变更时，**整体归档旧树、重建新树**，不原地打标签、不往旧结构里加新子目录。
- 归档 = 移到 `归档/` 或标注「已取代」，保留历史不删除。
- 好处：新树干净、无历史包袱；旧材料可追溯。

## A3 引用完整性检查（提交前必查）

- **移动/重命名文件或目录后，必须跑断链检查**：`rg -n "<旧名>" .` 确认无残留旧路径引用（或全部更新）。
- 任何「迁移/改名」类任务收尾前，把断链检查写入**提交前 checklist**（落地清单阶段 2/3 有对应项）。
- 检查对象含：md 内链接、`README`/`AGENTS` 里的路径、登记表（目录索引/挂载登记）、脚本里的路径。
- **指向行随正本升版刷新**：README/索引中指向正本的行（版本指向、状态行）须随正本升版同步刷新；未刷新的按缺口登记，不得滞留旧版本号。

## A4 handoff 主线程指针

- `<实例根>/_workspace/_handoff/README.md` 是续接主题的唯一事实源。非该位置的同名 README 只能作为跳转，不得另立状态或索引。
- 顶部「**当前主线/下一任务**」指针必须直接链接到状态为「进行中」的续接文档；进行中索引行和该目标必须一致。
- 主线或状态变化时，同步更新目标续接文档、索引行和顶部指针。新会话只按该指针续接。
- 发现多个活跃索引、指针目标缺失或状态不一致时，报告 `HOF-001`，不得自行按启动目录或更新时间选择。

## A5 脚本路径从配置/登记读，不硬编码绝对路径

- 脚本里的外部路径**从配置/登记表读取**（如挂载登记 `07-VSCode工作区挂载登记.md`、数据源登记表），不硬编码绝对路径。
- 路径变更时：改登记表 + 跑同步脚本，不逐脚本手改。
- 参考实现：`04-工具/03-工作区治理/sync-vscode-workspace.ps1` 用 `$PSScriptRoot` 推导默认路径。

## A6 处理过程可追溯

- 任何清洗/转换/加工/整理，**留处理记录**：做了什么、DONE 了哪些、排除项是什么（写进续接文档或独立记录文件）。
- 机器可重跑优先：产出前确认有可重跑脚本/命令，支持 `--sample` 先跑通再全量。
- 结论性文档与机读数据分离：机读 CSV 落数据目录，结论 md 落文档目录。

## A7 文档语言与表达规范

> 适用：AI 生成的正式工程文档（需求/方案/总结/规则等）。目标是可检查、无空话、判断有依据。

1. **平实书面语**：不用口语、感叹、营销腔、排比修辞；正式文档不写「强大的」「极致」这类不可检查的修饰。
2. **术语准确稳定**：同一对象全文用同一术语；引入缩写/别名前先定义，不混用。**不为已有惯用说法的概念另造新词**（如把「性质」写成「形状」、把「章节划分」写成「功能域」）——表述需引入新词时，先查既有文档与术语表是否已有该概念的通用说法，有则沿用；确需新词（尚无通用说法的新概念）时在首次出现处定义。**术语名不含易变的具体值**（如规模「56」、版本号、日期）——具体值作当前规模/取值注记写在定义内，样本扩容或取值变更时术语不变。**术语表定义采用「种概念是（种差的）相邻属概念」陈述式**（逻辑学属加种差定义）：先以属概念定位，再以种差划界（如「基线库是插件容器库的一种，是实例库中已上线产品对应的插件代码包子集」）；操作性注记（判定口径、流程约束、锚点）置于定义句之后，不混入定义句。**术语统一登记（两层，v1.7）**：通用层 = `_workspace/_术语/通用-*.md`（模板权威，随模板分发，团队统一术语）；实例层 = `_workspace/_术语/实例-*.md`（实例唯一登记源，业务/项目专有）。引入新术语、发现撞词或歧义时先查通用层再查实例层，有则沿用，无则文档首现定义＋同批登记实例层；AI 在每个正式文档批收尾时检查本批新术语并补登记；在档术语的写法与定义以两层术语集仲裁，**通用层权威，实例层不得重定义**（实例确需不同含义的近形词，实例层登记撞词注记行避让）；AI 登记的条目属提议性质，人可改判；实例术语被证明跨实例通用时走回流提案上升通用层。文档内首次出现处给定义的要求不变，术语集不替代文档内定义。机制正本见 `_术语/README.md`。**表述不拟人化**：技术术语携带的拟人成分（如模块「职责」）属拟人化描述，存在中性替代词时改用中性技术词；人与参与者的正当语境和已固化技术名词（如守护进程、监听器）除外。
3. **一句一个主要判断**：长句拆短；一个句子只承载一个判断，判断与依据分句写。
4. **抽象术语附具体对象**：出现「可扩展性」「健壮性」等抽象词时，紧跟具体对象与可验证结果（如「支持新增数据源类型而不改清洗主流程」）。
5. **事实 / 假设 / 候选 / 待确认明确区分**：用「已知」「推测」「候选」「待确认」标注，**不把假设写成结论**。
6. **强度词规范**：`必须`/`不得`（硬约束）、`应`（推荐）、`可以`/`建议`（可选）、`待确认`（未定）；正式文档不用模棱两可的「尽量」「尽可能」指代硬约束。
7. **非技术读者场景例外**：面向非工程读者（业务方等）的文档按对象调整术语密度，但判断与依据的区分仍保留。
8. **生成后自检清单**：逐条过——是否有空泛口号 / 是否有超长句 / 术语是否漂移 / 是否有造词（第 2 条）/ 评价是否有依据 / 是否有机器文风特征（第 9 条）/ 是否有口吻乐观倾向（第 10 条）/ 是否有公文腔词与标题量级失配（第 11 条）/ 是否有可删的冗余句。
9. **去除机器生成文风**（2026-08-25 增补）：AI 起草的文档在符合上述条款外，还应消除四类典型机器文风——
   - **空洞高频词**：沉淀、收口、抓手、闭环（作动词）、赋能、拉通、对齐（泛用）、旅程、一体化、底座、旨在、致力于等——多数没有可验证的对象和动作，替换为具体行为或删除；
   - **机械结构**：每段总—分—总、逐段首先/其次/最后、段末复述段首、结尾强行升华——删除总结句和过渡句后信息不减少的，删除；
   - **直译句式**：「这是……的关键所在」「值得注意的是」「不仅……更……」「通过 X，实现了 Y，从而 Z」——拆为多个单判断短句；
   - **强调符号癖**：滥用破折号补充、引号/加粗强调非术语词——补充说明改独立句，强调只保留给术语与强度词。

   判断标准：删除该词或该句后，句子的可验证信息是否减少；不减少即删除或改写。文档中的既定术语不属机器文风，不得按本条误删。

10. **口吻中性**（2026-09-12 增补）：描述效果、工期与达成条件时，用中性、客观的口吻陈述事实，不使用带保证义务或弱化难度的表述——
    - 尚未实测的效果不写「承诺」「保证」「确保」；预判值写作「预期」，并注明实测来源与刷新条件；
    - 达成时间或效果尚不确定的，写「目前无法测算」或「尚未确定」，同时写明测算所需的数据或前提；
    - 范围外与不做的事项直接写「不做」「不含」，不用「不承诺」等否定式承诺句；
    - 交付物描述宁保守勿乐观，难度、限制与前置条件应随结论写明，不得只写有利面。

11. **去公文腔**（2026-09-12 增补）：工程文档不使用公告、通报等公文语体的词与句式——
    - 不用「披露」「兹」「特此」「予以」「莅临」「之际」等公文词，改用平实动词（如「披露」改「列出」「写明」）；
    - 标题不使用大范畴抽象词，应带具体对象与数量，使标题的量级与内容一致（如「共性问题」改「问题分类」）；
    - 判断标准：把该词或标题放进公告、通知里是否同样成立；成立则属公文腔，应改写。

典型改写对照（自检用）：

| 原写法 | 问题 | 改法 |
|---|---|---|
| 我们打造了强大的治理体系 | 空泛口号 | 治理规则现覆盖入口/索引/约束/续接 4 类（见 00-04） |
| 数据质量显著提升 | 无依据评价 | 清洗后字段缺失率由 12% 降至 3%（依据：2026-08 清洗记录） |
| 建议接入该方案 | 强度不明 | 建议接入该方案（候选 A；待确认：与原数据源兼容性） |
| 需要保证系统稳定 | 抽象无对象 | 需保证服务重启后挂载登记不丢失（验证：重启后跑同步脚本比对 folders） |
| 完成本模块能力的沉淀与收口 | 机器文风·空洞高频词 | 本模块的公共函数移入公共目录，接口清单更新至对应文档 |
| 旨在让流程更加顺畅 | 机器文风·直译腔 | 该流程支持从创建到归档的连续操作，无需中途切换工具 |
| 通过复用，实现了效率提升，从而缩短了周期 | 机器文风·链式长句 | 复用后各环节用时：环节 A 由 X 天降至 Y 天（依据：两次执行记录） |
| 各节描述结构按内容形状选用 | 造词（「内容形状」非既有说法） | 各节的描述结构按内容性质选用 |
| 本节按功能域组织（「功能域」已指插件功能划分） | 造词/撞词（一词两义） | 本节按功能层次（能力类别）组织 |
| 我方承诺拦截约三成问题 | 口吻乐观（尚未实测即承诺） | 预期可检出约三成（预判值，以试运行期实测刷新） |
| 我方不承诺减少处理轮次的达成时间 | 否定式承诺句 | 减少轮次所需时间目前无法测算，需缺陷结构与往返成本两项数据 |
